四、接口契约（                  🔴 第 1 周必须定死）
        学生团队散伙的第一原因不是能力不够，是两个人对同一个接口的理解不一样。
        下面这些约定第 1 周写进 README，之后不许单方面改。

4.1 统一响应体
{
    "code": 0,    // 0=成功，非 0=业务错误码
    "msg": "success",
    "data": { ... }   // 业务数据，失败时为 null
}

前端只判断 code === 0。

4.3 三个关键接口的字段

GET /api/room/{id}/state（前端每 2 秒轮询 · 张越扬写，陆豪+张宇恒用）

{
    "roomId": 1,
    "status": 1,
    "phase": 3,
    "currentRound": 2,
    "phaseDeadline": "2026-11-22T21:35:00",
    "players": [
      {"seat":1, "userId":10, "nickname":"小明", "characterName":"苏明轩",
       "avatarColor":"#c0392b", "isConnected":true}
    ],
    "npcList": [{"npcId":1, "name":"陈伯（管家）", "type":1, "remainQuota":15}],
    "myClueCount": 3
}

POST /api/game/ask-npc（陆豪写核心，张越扬提供 Redis 支撑）

// 请求
{ "npcId": 1, "question": "昨晚九点你在哪？" }


// 响应
{
  "code": 0,
  "data": {
        "npcName": "陈伯（管家）",
        "answer": "回您的话，二十一点十分老奴送完茶便回了仆人房……",
        "newClue": { "id": 9, "content": "陈伯的行踪：……" }, // 没有则为 null
        "remainQuota": 12,
        "latencyMs": 2340
    }
}

GET /api/game/role（张越扬写，张宇恒用）

{

    "privateSecret": "你的丝厂亏空了三万大洋……",
    "avatarColor": "#c0392b"

4.5 并行开发的关键：陆豪不等张越扬

第 2 周陆豪要做 ask-npc，但那时张越扬的房间/状态机可能还没写完。解决办法：

陆豪用假数据先调通：
- 房间 ID、用户 ID 写死
- 阶段校验先跳过
- Redis 配额先用本地变量代替
等张越扬的接口就绪，替换成真实调用即可

这就是接口契约要第 1 周定死的原因——契约清楚了，两个人才能真正并行。




五、Git 协作规则

分支模型
main              ← 只放能跑的版本，合并前必须本地跑通
├── feat/backend-core    ← 张越扬
├── feat/ai-npc      ← 陆豪
├── feat/frontend-ask   ← 陆豪（盘问页+讨论区）
├── feat/frontend-pages ← 张宇恒（6 个页面）
└── content/script      ← 张宇恒（剧本数据）

  1. 每人在自己分支开发，完成后合并到 main
  2. 合并前自己先跑一遍
  3. 不要直接往 main 推
  4. 每天至少合并一次——攒一周再合，冲突会要命

Commit 规范
feat: 新增房间创建与加入接口
fix: 修复投票时未校验房间阶段的问题
docs: 补充 README 的本地启动步骤
refactor: 抽取 Prompt 组装逻辑为独立 Service
test: 补充泄密拦截的单元测试
content: 修改陈伯的人设文本，减少主动展开
chore: 更新 Dockerfile 基础镜像区域

    评委复核代码看的就是这个历史，面试官翻你仓库第一眼看的也是这个。
